# Per-phase agent roster — agents, identities, grants, and the practices they run

## 0. What this doc must fit (inherited, not re-decided)

- **Two words** (round 57): the store's permission sets are **grants** (`owner` / `contributor` / `lander`); the roster's kinds are **agents**. The binding reads `agent → identity → grant`. An agent has a prompt; a credential holds a grant; **the builder holds none**.
- **Phases pick, consume and close make no model calls** — they are deterministic functions of (cards, ledger, config). An agent exists only where judgment is exercised.
- **Prompts are code**: versioned in the factory repo, provenance-stamped, changed by the same discipline as code; a run records the prompt version it ran.
- **One human gate**: the owner's signature at the sitting. Everything an agent produces is either mechanical (validated, journaled) or waits at a gate the schema already defines.
- **No silent capability**: an agent may call exactly what its grant allows; everything else it wants becomes a suggestion or an interrupt question.

## 2. The planner's invocation protocol — the one ceremony [proposed; round 28 rulings quoted in 03a]

Every invocation, in order: (1) **review its opens, principles and the ARC** (owner, round 28); (2) **the morning review** = `show Queue` — open questions · holds on the owner · closures pending review · withdrawals pending · cards blocked by any of those · dispositions since the last batch signature · inbox counts by source; (3) **triage the inbox** with the owner — every disposition together (round 28); (4) **the interview** — source the details the builder will need: the shape's required fields, `guidance` (avoid/risk/constraint with ids), `surfaces`, `depends_on`; what stays unanswered becomes `questions[]`, never an assumption (round 24's sourcing concern); (5) **compose the sitting** as `ratify(writes: [WriteRequest])` — releases, answers, accepted closures, guidance edits riding with ratifications; (6) **the dry run** — always, before presenting (round 48); the display shows per member: act · build hash · the gated diff · the tending/hold changes since the last signed entry (X1); (7) **"ready to ratify these N?"** — one signature; done. The planner's own standing lens: **efficiency of construction and execution** (round 42) — smallest sufficient cards, one call where one would work, budgets respected at composition time. Credentials at the ceremony (O-3, O-4): the non-dry `ratify` is **the owner's session credential at the sitting** — the signature verified against the `owner` binding is what makes the batch effective; and "with the owner" is enforced mechanically, not by convention — **dispositions and the non-dry `ratify` exist only in the interactive session**. The planner's own bot identity is the named seam for a future headless morning-review report, and holds `contributor` for that seam only.

## 3. The adversarial practice — standing discipline [proposed; gajae follow-up 4 adopted]

- **Per story** (the line): one reviewer pass, findings typed and cited to guidance ids and rule ids; **reconcile is one bounded round** (ratified flow); unresolved disagreement is `disputed`, never quietly dropped. The exit is determined (O-6): on the second pass, every blocking finding `fixed` — or `refuted` with the reviewer's concurrence — is `pass`; any blocking finding still asserted ends the run `failed:review-disputed`, landing as a `disputed` event (03 §6) with the reconcile report attached; disputed and failed cards are listed in the queue section beside closures pending review, and unstick at the sitting — the owner re-ratifies with guidance or adopts the finding as a card revision.
- **Deterministic gates around the model calls** (M-3, M-4): a plan-lint — schema-valid, touched-surfaces subset, traceability complete, all existing functions — runs **before** the refuter and judge calls; a mechanically invalid plan loops back on a function refusal, never on a model call. And an empty findings artifact **skips reconcile** — zero findings, zero calls, decided by a function of the artifact.
- **The ratchet** (gajae): every review names what the previous review's fixes broke or missed; a finding class that recurs twice becomes a validator rule or a guidance template, not a third finding.
- **The bloat refuter rides every design-level review** (round 42): each mechanism priced for construction and execution; flows-vs-functions; one-home-per-fact. Proven in rounds 5–6 and the 04 round; now standing.
- **Scope-inflation counter-review** (gajae): the reviewer checks the diff against `surfaces` and the plan's traceability matrix — work beyond the card is a finding even when correct.
- **Cross-lineage input into the gate** (gajae, sharpened per M-2): what the defaults implement — and what the practice is — is **a refutation from a different lineage than producer and judge feeding the gating verdict** (Sonnet refutes, Opus judges), not a different-family judge; recorded in the run record's `phases[]`, so any deviation is visible to calibration telemetry.
- Review artifacts are evidence, preserved under `review-artifacts/` with a README naming the oracles — the conformance-corpus practice generalized.
- **Per-adapter capability matrix [owner-ratified 2026-08-27 (7be.3)]:** every execution adapter declares what it preserves and what degrades as capability rows the conformance suite checks — declared degradation, never silent; the hooks-in-runner unknown becomes a row, not a standing unknown (T-C6; `../research/isidium-review-2026-08-27.md` §3).
- **Typed negative findings [owner-ratified 2026-08-27 (7be.3)]:** the close report records what was checked and found absent — typed, indexed by the memory tier (T-B12); absence of a finding is evidence only when it was looked for (`../research/isidium-review-2026-08-27.md` §3).
- **The assurance witness — at first tenant [owner-ratified 2026-08-27 (7be.3)]:** a standing read-only declared-vs-practiced governance check; deferred to the first tenant by design, the seam named now (`../research/isidium-review-2026-08-27.md` §3).

## 4. Identities — the binding table [proposed; details to G7 and agent-station by pointer]

- Every non-interactive bot writing code: **own git identity + own forge account** (owner directive 2026-08-16; catalog 0.3); commits authored by it, `Co-Authored-By` trailers at ingest are corroboration (1.15).
- **Identity only where a credential or a write exists** (M-9; M-12 verified): forge accounts are **builder-only** — the directive's own scope is bots *writing code*. The plan author's, plan-refuter's and judge's "identities" are **run-record names** (agent kind + prompt version + model), not credentials; per-story findings ride the run record and are landed by the lander, never committed by the reviewer.
- Agents in the owner's interactive session act under the session credential — `contributor`, never `owner` (03 §1.3).
- The binding `agent → identity → grant` lives in the realm (bindings in the policy chain, 03 §1.12); the roster names *which agent kinds exist and what each may hold* — the enforcement is the store's, the storage is agent-station's (by pointer).
- A run record names: agent kind, effort, prompt version, model, per-phase tokens/cost/duration, and the judge's verdicts (section 6 of 03; M-5–M-8 applied) — the telemetry the tuning loop reads.
