## 0. Verdict in one paragraph

**The config surface is buildable from the text alone and survives the efficiency lens** — the validator, resolver, `init` (the section-3 file reproduced byte-exactly), tenant immutability, unsigned-no-effect, `ext-schema-changed` vs governed-no-rehash, both reserved-key seams, the declare-vs-use backend behavior and the grant-matrix swap point all pinned to one implementation on the first build; the one-home discipline held where 03 pinned it (board caps, verbs, grants correctly absent; the ratifier pin one home; the tenant mirror justified); the weights sum to exactly 1000; nothing on the config path is O(cards) except the two signed re-hash acts, by design. **Three findings are shape-changing.** Two are the same defect seen from two sides — *what a "default" is*: (Y1) the lean default leaves "every key is policy" with a hole exactly the width of the binary's built-ins — a toolkit release changing a default ships unsigned effective policy, while exact-assert pins force a signed edit per tenant per release; (Y2) shapes, ladder levels and origin names are declared both in their own tables and in `[extensions]`, whose hash can unratify cards — an enum declaration should never re-hash a card. The third (Y3) is the registry's reach: the four-part schema-of-schemas cannot express `config@1` itself (no defaults, enums, patterns, ranges, subset-of, dynamic sub-tables, array-of-tables) — demonstrated mechanically with 56 refusals — so section 4's "drift impossible by construction" does not yet hold. The remaining 34 findings are pins; the sharpest: the first entry's act (`config-policy` vs the recompute table's `created`), the section-3 file is a template that fails its own inventory (placeholders), first-match vs `governed-overlap`, `fields` granularity on policy entries (inside the chain hash — two readings, two `h`), and the six `config.*` rule ids covering a third of the implied refusals.

## 1. Shape-changing calls — for the owner (Y-series)

| # | Call | Raised by | Recommendation |
|---|---|---|---|
| Y1 | **What the toolkit pins assert, and where defaults live.** (a) *Exact-assert*: `[toolkit]` pins must equal the running binary — every toolkit release forces one signed config edit per tenant (real ceremony, per release, forever). (b) *Record/minimum*: pins are a compatibility floor — releases are free, but a release that changes a built-in default silently changes every lean tenant's effective policy unsigned. (c) *Defaults live in the adopted schema, not the binary*: `config@<n>` — already content-addressed, already signed into policy at adoption — carries the default for every key it declares; the resolver reads defaults from the tenant's **adopted** schema version, the binary merely ships schema copies. A release never changes effective policy (your adopted version pins it); moving to better defaults = adopting `config@<n+1>` = one signed manifest edit, the mechanism that already exists; toolkit pins relax to a compatibility floor with one mismatch rule (`config.toolkit-incompatible`). | L2-1 | **owner — recommend (c).** Closes the unsigned-drift hole with zero new ceremony and no new mechanism. |
| Y2 | **Ext-enum declarations stored once, not twice.** Today a tenant shape, ladder level or origin name is declared in its own table *and* implied under `[extensions]`, whose canonical hash (`ext_schema_hash`) sits in every fingerprint — so declaring a new shape can send every card `unratified` pending a signed re-hash. Option (a): declare once, locally (`[shapes]`, `[ladder]`, `[origin]`); `[extensions]` restricted to `x.*` field schemas; `ext_schema_hash` covers only those — adding a shape, level or origin name never re-hashes a card (a card using an undeclared name simply fails validation). Option (b): keep 03's wording — everything `Ext` lives in `[extensions]` — accepting O(cards) re-hash exposure per enum declaration. | L2-2 | **owner — recommend (a).** One home per declaration; the re-hash stays reserved for what actually changes card content semantics (`x.*` classes). Needs a matching one-line amendment in 03's extension section. |
| Y3 | **The registry's constraint vocabulary.** `registry@1`'s four parts (head/tables/sections/footer) express the six v1 document *forms* but not `config@1`'s own rules: no slot for defaults, enums, patterns, integer ranges, subset-of, dynamic sub-tables (`[signer.<backend>]`, `[shapes.<lint>]`), array-of-tables semantics, or change-semantics hooks — the implementer showed the constraint-bearing `config@1` fails it with 56 refusals. Option (a): extend `registry@1` with a **closed** constraint vocabulary (default · enum · pattern · range · subset-of · dynamic-table · array-of-tables · immutable · reserved) — the fixed point re-proved over the full form; stays far short of JSON-Schema sprawl. Option (b): keep the four-part shape and hand-code `config@1`'s constraints in the validator — the "one schema, three consumers / drift impossible" claim is then withdrawn for config and holds only for the document forms. | K-11 | **owner — recommend (a)** — Y1(c) depends on schemas carrying defaults, and the planner's tool-call schema needs the enums anyway; (b) would re-open the drift the registry exists to close. |
