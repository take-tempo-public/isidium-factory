## 0. Verdict in one paragraph

The core is now **interoperable**: two independent clean-room hashers agree byte-for-byte on build and claims hashes across the whole corpus, the footer parses and appends as a one-line insertion preserving CRLF, every ruled change from rounds 26–39 shows up exactly where the oracle is expected to disagree and nowhere else, and every footer trick the attacker built — second section, fence inside Updates, forged `history` block, unterminated fence, CRLF games — yields a typed error on the attacker's own card. Round 3's gate holes are closed: within-tenant replay of a signature across acts, cards, time and rollback is dead. What round 4 found is the layer *around* the gate, and it is not subtle. **The design has no way to author a card.** The governed store says only the store server writes; the command set has no call that writes Scope, scenarios, guidance or answers; the hook-append that draft-3 relies on is exactly the bypass 03b forbids; promotion has no command and no act. The bridge — which depends on "the normal process" — cannot be walked. **The tuple binds too little of what the owner is attesting to**: not the claims (so an accepted closure can be edited after acceptance), not the summary (so a verified summary can be swapped), not the tenant, not the journal head, and its `at` is chosen by the session. **Both signer backends leave the agent's own process in the trust path**: `remote-totp` binds the code to the request the *agent* sent, and `tpm-hello` proves presence, not intent. **On the workstation the journal has no enforcer the agent doesn't control** — a SQLite file under the shared OS identity, queried from a local server the agent could stand in for — and policy (roles, runners, signer address, the governed manifest, the `toolkit.lock` pin) is unsigned or signed only by a git commit key, the collapse U4 removed. And the board, rendered on six bridged sartor cards, **hides the owner's entire queue**: `held` outranks `has-questions`, so four of six cards with open questions show none; the morning review never lists open questions, `needs = "owner"`, or holds awaiting release. Nine calls are the owner's (section 1); the rest is pinning (section 2). The sartor cut-over list (section 4) is the bridge session's input, persisted here.

## 2. Fill worklist for draft-4 (mechanics; no ruling needed)

**Recompute, chain, tuple**
- H1 The recompute function, written down: `created` → `fields` = every key present (sorted) + `scope` if present; `amended` → keys whose canonical value changed + `scope` / `updates`; the `via × diff → act` table; two entries in one commit ordered `amended` then the ratifier-only act; `fields` for promotion = `["id", "promoted_from", "status"]` with `draft_key` listed as removed. (I2-B1, W-U4)
- H2 Repair: the `repaired` entry itself chains from `h_k`; `seq` continues; `restart_from ≥ history_head.seq` (hook/ingest refuse); stale entries between `k` and the repair are "unverifiable, covered". (I2-D1, G2-V19)

- H4 `att`: content, encoding, lifetime; an expired attestation whose window covered `at` verifies; when the realm is reachable the ledger re-checks bindings (`att` is a cache, not authority); revocation named. (I2-nit, G2-V2, W-U11)
